## §0 要解决的问题，三句话

1. **平铺**：现在 3 个题组（五行生克 25 题、三爻定八卦 8 题、六爻定世应 64 题）在预览站是一个下拉框里的三个并列选项（`apps/preview/src/drill.ts` 的 `buildDrillPlan`）。用户看到的是「题组」，不是「下一步该做什么」。
2. **无处可挂**：「达到某能力才解锁下一关」这件事，在 V0.1 §10.1 里写成了 `Skill → Lesson → Exercise` 的链条，但**链条中间那一环没有落库对象**——所以 Mastery 阈值现在只能挂在空气上。缺口清单 C1 的原话：「`Path/Unit/Lesson` 会在做 V0.4 时立刻需要」。
3. **B0 无法共享**：V0.2 §7 要求「B0 需作为跨体系共享单元（一次编写，所有体系复用）」。没有 `Unit` 实体，B0 只能是一句愿望。

**不做会怎样（具体）：** 97 题永远只能按「题组」切片；`SkillEdge` 里那唯一一条 `requires_mastery_threshold` 永远只是数据；内容补到六爻纳甲/六亲时，题组数会变成 8–10 个，用户面对的是**更长的下拉框**，不是课程。

## §1 五个硬约束（先讲约束，再讲字段）

字段形状不是随便定的。以下五条从**已有文档与已有代码**推出来，每一条都能在代码里指到出处。

| # | 约束 | 出处（可核对） |
|---|---|---|
| **L1** | 课程实体**不得携带任何术数知识**。它只说明「先做哪些题、达到什么程度再往下」。 | V0.1 §2：Layer 3 可被整体替换而不动 Layer 1/2。课程里若写进「乾为天属金」这类内容，换一套课程设计就得重写知识层 |
| **L2** | 课程实体**引用已有实体，不复制它们的字段**。`Lesson` 里不能有「本题正确答案」或「本技能判分方式」的副本。 | `Exercise.answer_key` / `Skill.judging_mode` 已存在；复制 = 两处真相，改一处另一处不知情（ADR-0023 的「防分叉」就是为这类问题设的） |
| **L3** | `Lesson` **不能引用「具体某一道生成的题」**，只能引用 `ExerciseTemplate` + 选取规则。 | **生成题不是内容条目**：`ExerciseInstance`（`layer3/exercise-template.ts`）由 `generateExercises()` 在运行时产出，**不落库进 `bundle.json`**。硬要引用，就得把 97 道题写进内容库——那会推翻 ADR-0021 的整个内容经济学（V0.2 §5.6：题目量来自关系表组合，边际成本极低） |
| **L4** | 三个实体**携带 Layer 0 元数据**（`entityBaseSchema`：`id` + `provenance`）。 | `layer0/provenance.ts` 的原话：「每个 Layer 1 / 2 / 3 实体都必须携带」。课程属 Layer 3，没有例外 |
| **L5** | **不给 `Exercise` / `ExerciseTemplate` 加反向指针**（不加 `lesson_id`）。 | 一题可测多 Skill、一题可被多课用（V0.1 §1：Exercise 与 Skill 是多对多）；反向指针把多对多压成一对多。且 `Exercise` 的注释里已声明边界：「一个 Exercise 不隶属于任何课程结构，它就是一道能答的题」（ADR-0016） |

**L4 的一个真实麻烦，必须先处理：** `provenance.sources[]` 为空时，CI 规则 **R1c** 会发 warning（`validate/rules.ts`）。而「先上五行生克、后上六爻」这种**排课顺序**没有文献可引——它不是知识论断。若照搬，每门课都会带一串无意义的 warning，warning 数量一多就没人看了。

> **处理（沿用已有先例）：** `rules.ts` 的 R1c 已经为一类实体开过口子——`confusable_with`（预设易混对）的 id 前缀被识别为「教学假设」，报错文案改为「无文献来源（这是正常的）：它的验证方式是**实测数据**」。课程实体**同属此类**：它们的正确性由「学习者是否走得下去」检验，不由文献检验。
>
> **落地方式：** R1c 的豁免判定从「id 前缀是 `confusable_with `」改为「实体类型 ∈ {预设易混对, Path, Unit, Lesson}」（实现上就是给 `checkProvenance` 多传一个 `kind` 参数，或在 `entity_id` 之外增加 `entity_kind` 判定——后者更稳，因为现在 `entity_kind` 已经传进来了）。
>
> **代价：** 课程实体不再享受「无来源 → 提醒」这条护栏。**缓解：** 课程实体**不携带**知识论断（L1），所以它本来就不该有文献来源；真正的知识论断留在被它引用的内容条目里，那些仍然受 R1a/R1b/R19 管。

## §2 三个实体：具体 JSON 形状

> 命名风格对齐 `bundle.json` 现状：顶层键 `snake_case` 复数（`exercise_templates` / `assessment_specs` / `rule_test_sets`）；实体 id 用「前缀.路径」点号风格（`sym.bagua.乾` / `skill.liuyao.trigram-by-yao` / `tpl.liuyao.trigram` / `ex.transfer.strength-leo` / `spec.b0.s4`）。
>
> **字段命名原则：** 引用的字段一律 `<目标>_id` 或 `<目标>_ids`（`skill_ids` / `assessment_spec_id` / `template_id`），与现有实体一致；**不引入新的命名惯例**。

### §2.1 Path（学习路径）

```json
{
  "id": "path.liuyao.rules-first",
  "name": "六爻 · 规则密集型入门",
  "system_id": "system.liuyao",
  "goal": "把「爻 → 卦 → 世应」这条确定性链条走完：每一环都由规则算出，不靠记忆。",
  "unit_ids": [
    "unit.b0.s4",
    "unit.liuyao.trigram",
    "unit.liuyao.hexagram"
  ],
  "entry_unit_id": "unit.b0.s4",
  "provenance": { "...": "见 §2.5" }
}
```

| 字段 | 类型 | 必填 | 说明与依据 |
|---|---|---|---|
| `id` | string | ✅ | 前缀 `path.` |
| `name` | string | ✅ | 展示名 |
| `system_id` | string | ⭕ | 可空。跨体系 Path（例如「东西方迁移」）没有单一体系。**空值有 CI 校验**（R21：引用的 system 必须存在） |
| `goal` | string | ✅ | 自然语言。**必须同时出现在 `content_texts`**（见 §7 R28） |
| `unit_ids` | string[] | ✅ ≥1 | **有序**。顺序即课程顺序（见 §3.4 为什么不用 `order` 字段） |
| `entry_unit_id` | string | ✅ | 必须是 `unit_ids` 的一个元素（R22） |
| `provenance` | Provenance | ✅ | L4 |

**为什么 Path 也要是一等实体，而不只是一个数组？** 因为同一个 `Unit` 会出现在多条 Path 里——这正是 V0.1 §2 那句「SkillGraph 是 DAG，课程顺序只是它的一个线性化；同一 DAG 可以排成不同 Path」的落点。B0 基础层单元同时属于「六爻入门」和「塔罗入门」两条 Path，是**设计要求**（V0.2 §7），不是巧合。

### §2.2 Unit（单元）

```json
{
  "id": "unit.liuyao.hexagram",
  "name": "由六爻定本卦与世应",
  "unit_kind": "普通",
  "stage": 2,
  "system_id": "system.liuyao",
  "goal": "能由六爻阴阳定出本卦（卦名、上卦、下卦、所属宫），并说出世爻与应爻各在第几爻。",
  "skill_ids": ["skill.liuyao.hexagram-by-yao"],
  "lesson_ids": ["lesson.liuyao.hexagram.01", "lesson.liuyao.hexagram.02"],
  "entry_lesson_id": "lesson.liuyao.hexagram.01",
  "provenance": { "...": "见 §2.5" }
}
```

> 上面这个例子里，**同一个题源（`tpl.liuyao.hexagram`，64 题）被拆成两课**：`.01` 只练「本宫」（8 题），`.02` 练其余位次（56 题里取 10 道）。拆课靠的是 `rule.table` 里已有的 `position_kind` 列——这正是对缺口 A7「97 题平铺」的正面处理（见 §3.3 的 `table-filter` 与 §8.5 的完整落地形态）。

| 字段 | 类型 | 必填 | 说明与依据 |
|---|---|---|---|
| `id` | string | ✅ | 前缀 `unit.` |
| `name` | string | ✅ | 展示名 |
| `unit_kind` | enum | ✅ | `基础` / `普通` / `流派对比` / `跨体系迁移` / `伦理必修`。**这是 V0.4 引入的最重要的一个字段**——它让 ADR-0006 的「流派对比是新的课程形态」和 V0 的「伦理必修关卡」从散文变成可校验的数据（§6、§7） |
| `stage` | 0–6 | ✅ | 对应 V0.1 §6 的 7 个阶段。**它是声明标签，不是评分维度**（见下方说明） |
| `system_id` | string | ⭕ | 条件必填（R24/R25）：`unit_kind = 基础` 时必须**为空**（B0 是跨体系共享的，V0.2 §2）；`流派对比` / `跨体系迁移` 时必须填 |
| `goal` | string | ✅ | 自然语言；进 `content_texts` |
| `skill_ids` | string[] | ✅ ≥1 | 本单元要让用户习得的一组 Skill（V0 术语表对「单元」的定义就是「目标是让用户习得一组 Skill」）。**它同时是 `path_mastery` 判据的技能来源**（§4.3） |
| `lesson_ids` | string[] | ✅ ≥1 | **有序** |
| `entry_lesson_id` | string | ✅ | 必须是 `lesson_ids` 的元素 |
| `provenance` | Provenance | ✅ | L4 |

**`stage` 为什么是声明标签而不是评分维度（一个重要取舍）：**

V0.1 §6 把阶段定义为「阶段之间由 Mastery 向量阈值判定，不由课程完成度判定」。这句话有两个部分：**阈值判定**必须可执行（→ §4 的 `unlock_rule`），**阶段编号**则是一个**教学意图的标签**（「这门课我把它放在第几个阶段」）。

> **倾向：`stage` 作为 Unit 上的**作者声明**（由人填），其判断力**完全由 `unlock_rule` 的 mastery 阈值承担**。CI 只能校验它的**内部一致性**（同一条 Path 内不得倒挂，R27），**不校验**「用户的 stage 是多少」——因为那需要一套新的评分系统，而本文档的首要禁令就是「不新造评分」。
>
> **代价：** 一个作者可以把一门难的课标成 stage 1，CI 不会拦。**缓解：** R27 会拦住「同一 Path 内 stage 与难度键倒挂」，而难度键里含**可计算量**（§5），所以纯手工误标的空间被压缩到「同一个档位内部」。**这条是我给的折中，若你要更强的一致性，只能引入 stage 判据（= 新评分系统），我不建议。**

> **Unit 没有 `unlock_rule`（有意的）：** 单元级门槛落在**入口课**（`entry_lesson_id` 那一课）的 `unlock_rule` 上。理由是「一个门槛只在一处表达」——若 Unit 与 Lesson 各有一套解锁条件，两者矛盾时没有人知道该听谁的（ADR-0023 防分叉的同一逻辑）。ADR-0006 要求的「达 B2 才解锁流派对比」因此写成：**该单元入口课的 `unlock_rule = { type: 'path_mastery', ... }`**（§6.2 第 3 条、§7 R24①）。

### §2.3 Lesson（关卡）

```json
{
  "id": "lesson.b0.s4.01",
  "title": "两个五行之间在做什么",
  "summary": "给定任意两个五行符号，判断二者之间的生克关系与方向，并说出依据是哪一条闭循环。",
  "skill_ids": ["skill.b0.s4.wuxing-direction"],
  "assessment_spec_id": "spec.b0.s4",
  "question_sources": [
    { "template_id": "tpl.b0.s4.wuxing-relation", "count": 5, "selection": "strided" }
  ],
  "exercise_ids": [],
  "unlock_rule": { "type": "entry" },
  "completion_rule": {
    "type": "mastery_threshold",
    "skill_id": "skill.b0.s4.wuxing-direction",
    "dimension": "应用",
    "min_value": 0.8,
    "min_samples": 3
  },
  "provenance": { "...": "见 §2.5" }
}
```

| 字段 | 类型 | 必填 | 说明与依据 |
|---|---|---|---|
| `id` | string | ✅ | 前缀 `lesson.` |
| `title` | string | ✅ | 展示名 |
| `summary` | string | ✅ | 自然语言；进 `content_texts`（R28） |
| `skill_ids` | string[] | ✅ ≥1 | 本课练哪些 Skill。**必须被 `assessment_spec_id` 覆盖**（复用 R12 的检查思路：题目的 Skill 必须在规约的 `skill_ids` 内） |
| `assessment_spec_id` | string | ✅ | 本课用哪份评测规约（`AssessmentSpec`）。显式引用而非从 Skill 推导——`Exercise` 已经这么做了，理由同（M16：同一 Skill 可有入门规约与流派对比规约两份） |
| `question_sources` | 数组 | ✅（可与 `exercise_ids` 二选一） | 生成题的来源：`{template_id, count, selection, filter?}`。**见 §3，这是本文档的核心设计** |
| `exercise_ids` | string[] | ⭕ 默认 `[]` | 手写题（`bundle.exercises` 里已有的，如 `ex.transfer.strength-leo`）。跨体系四段式关卡与流派对比关卡的题多半是手写的 |
| `unlock_rule` | 联合类型 | ✅ | §4.2 |
| `completion_rule` | 联合类型 | ✅ | 通关判据。**不得为 `entry`**（R23）——没有判据的通关等于没有通关 |
| `sample_kind` | `'A'` / `'B'` | ⭕ | **仅 `unit_kind = 基础` 的课必填**（ADR-0013 的 A 类/B 类样本）。B 类必须带 `school_id`/`controversy_flag` 的证据链，R26 负责拦 |
| `school_ids` | string[] | ⭕ | 流派对比课必填 ≥2（例外：体系内部不自洽，§6.4） |
| `divergence_kind` | enum | ⭕ | `inter_school` / `intra_school_inconsistency`（§6.4） |
| `divergence_rule_ids` | string[] | ⭕ | 流派对比课必填 ≥1：**分歧落在哪几条 `Rule` 上**。这是 V0.1 §16.2 新题型「指出分歧源于哪一步规则」的数据化 |
| `provenance` | Provenance | ✅ | L4 |

**刻意的缺席字段（这是设计决定，不是遗漏）：**

| 没设的字段 | 为什么 |
|---|---|
| `unit_id` | 顺序只存在于 `Unit.lesson_ids` 的**数组次序**里。若 Lesson 带 `unit_id`，同一个 Lesson 就只能属于一个 Unit，把 V0.1 §2 的「线性化」写死成唯一一条；而且「数组顺序」与「order 字段」并存必然分叉（ADR-0023 防的就是这类） |
| `difficulty` / `difficulty_band` | **不设人工难度字段**。难度必须由**可计算量**得出（§5），否则就是 97 个拍出来的数字，既无法校验也无法校准 |
| `estimated_minutes` | 不设。学习时长**没有数据支撑**，写一个数就是假数字（与 `mastery.ts`「宁可不给数字，也不给假数字」同一条原则）。要看时长就看**实测**：`Attempt.latency_ms`（已落库）→ `analysis.latencyByKind` → 预览站数据面板已经在显示「按题型的中位耗时 / p90」 |
| `order` | 见 `unit_id` 行 |
| `lesson_kind` / `narrative_type` | 属 V0.7/V1.0 的表现层设计，Layer 3 不需要 |

```
  自然语言字段（Path.goal / Unit.goal / Lesson.title|summary）──▶ content_texts[]
                                                                （R9 禁用语检查的唯一入口）

  Exercise / ExerciseTemplate ──✗──▶ Lesson    ← 反向指针**不建**（L5）
  ExerciseInstance（生成题）  ──✗──▶ 任何内容实体 ← 不落库（L3）
```

### §2.5 `provenance` 在课程实体上写什么

三个实体都用与现有实体完全相同的 `provenance` 形状（`layer0/provenance.ts` 的 `provenanceSchema`），但**内容语义不同**：

```json
{
  "sources": [],
  "source_strength": "低",
  "controversy_flag": false,
  "review_status": "draft",
  "authored_by": "human",
  "version": 1
}
```

| 字段 | 课程实体上的取值与理由 |
|---|---|
| `sources` | **允许为空**（§1 的 R1c 豁免）。排课顺序没有文献可引 |
| `source_strength` | `低`——不是知识论断，不强 |
| `controversy_flag` | 通常 `false`。**例外**：流派对比课的 `Unit` 若并列两派取法，应标 `true` 并把分歧点写进 `controversy_note`（认识论原则 4：争议不得伪装成定论）。这一条建议进 R24 |
| `review_status` | `draft`。课程设计同样是「AI 可起草、人工才能升 `reviewed`」的对象——**不做例外**。ADR-0016 的先例在此：`Exercise` 也是 draft |
| `authored_by` | `human` / `ai-candidate`（**AI 起草的课程存不进 `reviewed`**，R1b 管） |

> ⚠️ **必须做的连带改动：** `validate/rules.ts` 里的 `layer0Groups` 数组是**手工列出的实体清单**，而手工清单会漏——`exercise` / `exercise_template` 就漏过一轮（它们的 schema **都带 `provenance`**、数据里也都有，却不在清单里，于是 R1a/R1b/R19 对它们完全不生效：**一道题可以被直接标成 `reviewed` 而不需要任何人工复核记录**，而题目恰是玩家实际作答、最该有人签字的对象）。
>
> 这一漏项在工作区里已由另一处改动补上（`rules.ts` 的 `layer0Groups` 现含 `['exercise', …]` 与 `['exercise_template', …]`，并附了说明注释）。**新增 `Path` / `Unit` / `Lesson` 三类实体时，必须同样把它们加进这张表**——否则新实体携带了 `provenance` 却无人校验，那就是缺口清单 C1 那句话的翻版：**「声明了但没有落库对象」，只是换成了「有字段但没人管」**。

## §3 题目如何被编排进 Lesson（本文档的核心）

### §3.1 一句话答案

> **`Lesson` 引用的是模板（`ExerciseTemplate`），加上一条「选几道、怎么选」的确定性问题选取规则；具体是哪几道题，由生成器在运行时按同一份内容库重算。**

```
Lesson.question_sources[] = [{ template_id, count, selection, filter? }]
                                   │
            运行时：generateExercises(bundle, {templateId}) → ExerciseInstance[]
                                   │
                    selectInstances(instances, {count, selection, filter}) → 本课实际呈现的题
```

三条性质必须同时成立，缺一条这个设计就站不住：

| 性质 | 为什么必须 |
|---|---|
| **确定性** | 同一份 `bundle.json` + 同一个 Lesson ⇒ **同一批题、同一顺序**。有 `generate/drill.ts` 的既有保证（「确定性：同一 content bundle → 同一批题目（顺序稳定、id 稳定），有测试锁住」），选取函数必须同规格 |
| **不产生知识** | 生成器「不产生任何术数知识，只是在已存在的**关系边/规则表**上做组合」——内容库里没有的关系，就出不成题。课程只是**引用**，所以课程也不能绕过这条 |
| **可回溯** | 历史上「我做过哪几道题」必须能精确复现。**这一条已经解决了**：`Attempt` 按 ADR-0024 冗余存了 `exercise_id` + `template_id`；本文档只需再加 `lesson_id`（§4.6） |

### §3.2 为什么不能引用「具体生成的题」（三条代码级理由）

1. **生成题不是内容条目。** `ExerciseInstance` 由 `generateExercises()` 产出，`bundle.json` 里**没有它的位置**（`ContentBundle` 的 20 个数组键里没有 `exercise_instances`）。若课程要引用具体题，就必须把 97 道题写进内容库——而 `tpl.b0.s4.wuxing-relation` 那 25 道题「只是同一张关系表的 25 个投影」（`exercise-template.ts` 的原话），手写它们**只会引入抄错答案的可能**。
2. **内容库会增长，课程不该跟着改。** 未来补上纳甲表、六亲表，对应模板的题量会从 25 变成 100+。若课程硬编码了 10 道题，补内容时课程要人工重写；若课程只声明「10 道，等距取样」，**补内容后自动覆盖新题**。
3. **引用具体题会让「取不存在的题」成为一种静默失败。** 悬空引用现在靠 R10/R3 之类的规则拦；但生成题的 id 是 `${template.id}#${参数}` 拼出来的（例：`tpl.liuyao.trigram#111`），**它不是一个可被 CI 校验的内容条目**——写错了没有任何规则会报错，只会表现为「这一课少了一道题」。这正是缺口清单里点名过的失败形态（R3 曾是死规则、R18 那类「看起来完全正常的坏数据」）。

### §3.3 选题规则：4 种 `selection` + 1 个 `filter`

`selection` 是一个**封闭枚举**（可执行、可测试、可解释）：

| `selection` | 语义 | 用在哪 | 依据 |
|---|---|---|---|
| `all` | 全部生成题，按生成顺序 | 题量小的课（三爻定八卦：8 题） | 生成顺序 = 位组合升序，本身就是一个自然的覆盖序 |
| `strided` | **等距取样**：`step = max(1, floor(n / count))`，取 `instances[(i * step) % n]`（`i = 0 … count-1`） | 题量大的课（五行 25 → 取 5；六爻其余 56 → 取 10） | **预览站已经在用这个算法**（`buildDrillPlan` 的「确定性等距取样（不用随机，保证可复现）」）。V0.4 直接沿用这份公式，不发明新抽样 |
| `front` | 前 `count` 题 | 只在内容本身有序时用 | ⚠️ 慎用：对位组合题，取前 N = 只练低位组合（`000/001/010…`），**覆盖有系统偏差**。CI 无法识别这种偏差，只能靠作者自觉——因此建议默认不用 |
| `table-filter` | 先按 `filter` 筛规则表行，再按 `all`/`strided` 取 | **把 64 题的六爻课拆成有梯度的几课** | 见下方 |

`filter` 的形状（仅 `table-filter` 模式）：

```json
{ "template_id": "tpl.liuyao.hexagram", "count": 8, "selection": "table-filter",
  "filter": { "column": "position_kind", "in": ["本宫"] } }
```

**为什么 `table-filter` 是本文档唯一对生成器的新要求：** 六爻那 64 题现在是一门课。而 `rule.liuyao.hexagram` 的表里**已经有** `position_kind` 列，取值是 `本宫 / 一世 / 二世 / 三世 / 四世 / 五世 / 游魂 / 归魂`（**八宫卦序本身有古典引文**，见 `bundle.json` 的 `verifications` 与 `docs/复核记录-T1-T3.md` §三）。所以「按位次类型拆课」不需要任何新的术数知识、不需要新增列——只需生成器在枚举前按列筛行。约 10–20 行代码。

> **不做的更花哨的选取方式：** 「按上次答错的题优先」（= 复习排程，V0.6）、「按掌握度动态调整题量」（= 自适应，V0.5/V0.6）、「随机」（破坏确定性）。**明确不做**，见 §10。

### §3.4 `count` 的语义，以及「同一道题出现在两课」怎么办

- `count` = **本课最多做几道**。实际呈现数 = `min(count, 该题源可用题数)`。若筛完只剩 3 题而 `count = 8`，**用 3 题，不是报错**（过滤条件本来就可能有稀疏取值），但 CI 要求 `count ≥ 1` 且 `count ≤ template.max_instances`（R22）。**不允许**出现「筛完是 0 题」的课——那和 R17 拦的「死模板」是同一种病：内容存在但永远到不了用户。
- **同一道题出现在两课是完全允许的**，而且是**有意的**：同一题源 + 相同 `count` 的两次 `strided` 取样必然取到**同一批题**（`tpl.b0.s4.wuxing-relation` 25 题取 5 道时，`step = 5`，取到的是第 0/5/10/15/20 题）。将来若有第二门五行课（例如「方向专项」）沿用同一题源，重叠是必然的，这不构成错误：
  - **掌握度不受影响**：`Evidence` 按 `skill_id` + `dimension` 聚合（`computeSkillMastery`），不按题目聚合。
  - **积分自动衰减**：同一题重复作答按 `1/(1+n)` 衰减（`scoring.ts` 的重复衰减），所以「靠重复同一题刷分」在数学上不划算——这是 ADR-0021 已经挡住的。
  - **CI 不做「题不重复」的校验**：一题测多个 Skill（V0.1 §1），强行去重会逼课程设计者为了通过校验而改变教学意图。**这是有意的宽松。**

### §3.5 手写题怎么进课

`Lesson.exercise_ids` 直接引用 `bundle.exercises` 里的实体。已知的两个用例都在库里了：

| 题 | id | 它属于哪种课 |
|---|---|---|
| 塔罗↔占星的迁移练习 | `ex.transfer.strength-leo` | `unit_kind = 跨体系迁移` 的课（V0.1 §8.2 第 ④ 段的「迁移练习」） |
| 同一对边的**反向**练习 | `ex.reverse.strength-order` | 同上（第 ④ 段的「反向练习」，R3 双向确认的对象） |

→ **CI 规则 R25**：`unit_kind = 跨体系迁移` 的 Unit，其课必须至少引用**一对**（`is_transfer_exercise_of_edge_id` 与 `is_reverse_exercise_of_edge_id`）指向**同一条边**的题。这把 V0.1 §8.2 的四段式要求从「文档里的公式」变成「结构上缺了就构建失败」。

### §3.6 一个必须承认的代价：覆盖漂移

**问题：** 课程引用模板 ⇒ 内容库变了，同一课在不同时间给出的题**可能不同**。用户第 3 天做的第 4 题，与第 10 天做的第 4 题可能不是同一道。

**为什么可以接受：**

1. 完成度判据不看「做过哪些具体题」（§4.6 用 Attempt 覆盖 + Mastery 阈值），所以漂移不会让进度失效。
2. `Attempt` 冗余存了 `exercise_id` / `template_id` / `correct_label`（ADR-0024 的原话：「内容库会变，事后 join 会得到『当时不是这样』的结果。宁可冗余，也要可复现」）——**当时的题面与答案可精确复盘**。
3. 反方向的问题（课程硬编码题目、内容库改了导致题面过时）在这个设计里不存在。

**代价与缓解：**

| 代价 | 缓解 |
|---|---|
| 「上周做的那道题」找不回来（要找就得翻落库数据） | 数据面板已经支持导出 JSON（`dumpAll`），复盘走数据，不走界面 |
| 内容补齐后，某课的**完成度可能回退**（题集变大了） | 见 §4.6 的明确取舍：V0.4 **不引入** `LessonProgress` 实体，接受回退；V0.6 做 `ReviewItem` 时一并解决 |

## §4 解锁与推进条件

### §4.1 硬性要求：复用已有掌握度，不新造评分

已有的两套确定性机制（都在跑，有测试）：

| 机制 | 代码 | 取值 |
|---|---|---|
| **掌握度**：六维向量 | `layer4/mastery.ts` 的 `computeSkillMastery` | 维度 = 识别/回忆/应用/结构/迁移/生成；证据按置信度加权（规则判定 1.0 / AI 0.7 / 骨架 0.4）；样本 0–2 → **`数据不足`**，3–9 → `初步`，10+ → `稳定` |
| **积分**：纯规则函数 | `layer4/scoring.ts` 的 `scoreAttempt` | `认知负荷 × 难度 × 新额度 × 重复衰减`；掌握度未增长 → **0 分** |

> **本文档的解锁判据只吃第一个。** 具体理由见 §4.4。

### §4.2 `unlock_rule` 取值域

```jsonc
// 首课：无前置
{ "type": "entry" }

// 前置课完成
{ "type": "lesson_done", "lesson_id": "lesson.b0.s4.01" }
{ "type": "unit_done",   "unit_id":   "unit.b0.s4" }

// 能力门槛（最常用）
{ "type": "mastery_threshold",
  "skill_id": "skill.b0.s4.wuxing-direction",
  "dimension": "应用",
  "min_value": 0.8,
  "min_samples": 3 }

// 整条 Path 的能力门槛（流派对比课的「体系掌握度 ≥ B2」用它表达）
{ "type": "path_mastery",
  "path_id": "path.liuyao.rules-first",
  "dimensions": ["识别", "应用"],
  "min_value": 0.7,
  "min_samples": 3 }

// 组合
{ "type": "all_of", "rules": [ /* ... */ ] }
{ "type": "any_of", "rules": [ /* ... */ ] }
```

`completion_rule` 用**同一个联合类型**，但 CI 只允许 `mastery_threshold` 与 `all_of`（R23）：**通关必须有能力判据**。

### §4.3 判据怎么算：三态，不是两态

```
evaluateUnlock(bundle, lesson, userState) → {
  status: '已解锁' | '未解锁' | '判定中',
  reasons: string[],        // 直接可展示
  blockers: Blocker[]       // 每一条：判据 + 当前值 + 缺口
}
```

**三态是这个设计里最重要的一点。** 掌握度在样本 < 3 时**没有数字**（`display: '数据不足'`），因此解锁判据必须有第三态：

| 状态 | 触发条件 | UI 必须显示 |
|---|---|---|
| **已解锁** | 全部判据满足 | 「可以开始」 |
| **未解锁** | 至少一条判据**有估计值且未达标** | 「应用掌握度 0.62 / 0.80 —— 差 0.18」，并给出该差距由哪门课的哪个 Skill 承担 |
| **判定中** | 至少一条判据**样本不足**（`status = '数据不足'`），且没有判据已确定不达标 | 「再做 N 题才能判定」（N = `min_samples` − 当前样本数），**不给任何百分比** |

> **禁止的做法：** 把「数据不足」当成 0 分或当成满足。前者会让新用户一进来看见「未解锁」而不知道要做什么；后者等于假数字（`mastery.ts` 的模块注释：「宁可不给数字，也不给假数字」）。
>
> **这条要求直接决定实现：** `evaluateUnlock` 必须调用现有的 `dimensionValueOrNull()`（它本来就为这个场景写了：「用于积分计算：样本不足时不拿假数字算分，而是返回 0 并让调用方知道这是『未知』」）。**直接复用，不新增函数。**

### §4.4 积分为什么不进解锁判据（倾向 + 理由 + 代价）

| | 内容 |
|---|---|
| **倾向** | **不进。** `unlock_rule` 的取值域里**没有**任何 `points ≥ N` 的变体，且 R23 会拒掉未知 `type` |
| **理由 1** | V0.1 §10.3 原则 1 的原话：「激励必须挂在**能力增长**上，不能挂在**动作次数**上」。积分是**结果**，把它变成**资格**就立刻产生第二条优化路径：找最划算的题刷分去开门 |
| **理由 2** | 积分公式里含**已掌握内容的低额度**（`novelty = clamp(1 - mastery, 0.2, 1)`）。用它做门槛会出现荒谬情形：**越熟练越难解锁下一课**（因为熟练后每次得分趋 0） |
| **理由 3** | 积分**不落库到服务端**（D2 延后，现在是 IndexedDB 本地）。用它做门槛，换设备/清缓存就丢进度——而掌握度虽然是同一份本地数据，但其判据是**可重放的纯函数**（`computeSkillMastery(skillId, evidence[])`），语义上比「累计分数」稳固 |
| **代价** | 失去「用积分把学习行为串起来」的动机层。**缓解：** 积分仍**展示**（预览站已在显示累计积分与「为什么给 0 分」），V0.7 做激励映射时再说 |

### §4.5 混淆对为什么不进通关判据（与 V0.1 §10.1 的一处偏离）

V0.1 §10.1 的通关条件示例里写着「与『正逆位』相关的**混淆对频率 < 20%**」。**本文档不采纳它做判据**，理由三条：

1. **它会让「内容缺陷」变成「学习者的门槛」。** V0.1 §9.3 自己给了混淆对的三分支：混淆了**预设的**一对 → 教学正常；混淆了**未预设的**一对 → ⚠️ **内容或教学有问题**；跨体系混淆 → 过度迁移。第二、三种情况的责任在**内容侧**，拿它拦用户是把质检问题转嫁出去。
2. **它是聚合量，与掌握度不同源。** 「频率 < 20%」需要一个与六维向量无关的新尺度（阈值 20% 也是拍的），会让「为什么我没通关」出现第二套解释体系。本文档的首要禁令是「不新造评分」。
3. **现在恒为 0。** 混淆对的采集入口在 ADR-0024 已完成（`computeConfusionPairs` 三分支），但**真实数据仍为零**（缺口清单 E7 / C2-9）。一个恒真的判据等于没有判据。

> **代价与替代：** 失去「拦住带着系统性混淆继续往下走」的保险。**替代方案（非阻塞）：** 把混淆对作为**推荐输入**——某课结束时若检测到命中预设混淆对，界面上给出「建议先做这一课」的提示，**但它不挡路**。
>
> **这条偏离要你拍定**（§11 清单第 2 项）。

### §4.6 「完成」与「掌握」必须分开

| 概念 | 判据 | 产生掌握度吗 |
|---|---|---|
| **本课做过**（`lesson_done`） | 本课题集的**每一个实例**至少被作答过一次（按 `Attempt.exercise_id` + `lesson_id` 覆盖） | ❌ **不产生**。V0.1 §9.2：「掌握度只由 Evidence 更新。『看完一课』『连续签到』不产生掌握度」 |
| **本课通过**（`completion_rule`） | Mastery 阈值 | ✅ 由判分产生的 `Evidence` 更新 |

**为什么必须分开：** 若「做过」即可通关，用户会点完 10 道题一路往下走，最后拿着 0 掌握度到达实战关卡——这正是 V0.1 §6 那句「否则会教出『通关了但不会用』的用户」的具体形态。

**因此 `Attempt` 需要加两个字段（Layer 4 的改动）：**

```ts
// packages/domain/src/layer4/user-state.ts 的 attemptSchema
lesson_id: z.string().min(1).optional(),
path_id:   z.string().min(1).optional(),
```

| | 内容 |
|---|---|
| **为什么必须冗余存** | 一课可在多条 Path 里出现（§2.1），所以「用户当时在哪条路上」**无法事后从内容库唯一重建**。这与 ADR-0024 的理由逐字相同：「内容库会变，事后 join 会得到『当时不是这样』的结果。宁可冗余，也要可复现」 |
| **为什么不存 `unit_id`** | 它可由 `(path_id, lesson_id)` 推出（Unit 是 Path 下的节点）。**只冗余存不可推导的两项**——冗余是为了可复现，不是为了方便 |
| **代价** | `apps/preview/src/store.ts` 的 `DB_VERSION` 要 1 → 2（IndexedDB 的 schema 版本）。**现在改动的成本接近 0**，因为真实作答数据为零（E6）；等攒了两周数据再改就要写迁移 |

### §4.7 死锁防护：`min_samples` 的硬下限

**R23 要求所有 `mastery_threshold` / `path_mastery` 的 `min_samples ≥ 3`**（= `MIN_SAMPLES_FOR_ESTIMATE`）。

**为什么：** `min_samples < 3` 的判据**永远处于「数据不足」**（因为 `statusOf(2)` 返回 `数据不足`，`dimensionValueOrNull` 返回 `null`）——这门课就**永远解锁不了**。这是一个只有把门槛写进 schema 才拦得住的错误：它在内容上看起来完全正常（「做完 1 题就能进下一课」），运行时表现为「点不动，也不报错」。

## §5 难度曲线：可执行的排序与分档

### §5.1 为什么不能给题目人工标难度

1. **题目是生成的**（§3）。给 97 道生成题逐题标难度，等于每次补内容都要重标（纳甲/六亲进来会变成 300+ 题）。
2. **`difficulty` 现在只有两档**（`z.enum(['入门','进阶'])`），而 V0.1 §6 有 7 个阶段、§10.2 有 8 种题型。两档表达不了曲线。
3. **拍出来的难度无法校验**。项目已经有一份「我拍的数」清单（`docs/待采集数据.md` §二），里面明确写着「认知负荷权重 1/2/3/4/5 是拍的」「难度权重 1.0/1.5 是拍的」——**再拍一套课程难度，只是把待校准的清单加长**。

> **所以：难度曲线必须完全由「内容库里算得出来的量」构成。**

### §5.2 排序键（词典序，可计算，可校验）

```
sort_key(lesson) = [
    Unit.stage,                                        // ① 阶段（作者声明，整数 0–6）
    max(COGNITIVE_LOAD_WEIGHT[题.kind])                 // ② 认知负荷（已有常量，1–5）
      over 本课全部题源生成的实例,
    ceil(log2(本课题源**过滤后可用题数**)),            // ③ 内容空间量级（不是 count）
    (本课题源 difficulty 含「进阶」? 1 : 0)              // ④ 既有难度枚举（作为次序键，不是主序）
]
```

**每一项的出处与它到底在量什么：**

| # | 量 | 怎么算（全部现成） | 它在量什么 / 为什么可信 |
|---|---|---|---|
| ① | `Unit.stage` | 作者填，V0.1 §6 的 0–6 | **教学意图**。它排在第一序，因为「先教认符号再教定世应」是课程设计的职责，不该被算法推翻 |
| ② | 题型的认知负荷 | `scoring.ts` 的 `COGNITIVE_LOAD_WEIGHT`（识别 1 … 开放式解读 5） | **单题要求的操作复杂度**。这个常量已经在给积分加权，**同一份定义两处使用**，不会各说一套 |
| ③ | 内容空间量级 | `ceil(log2(题源过滤后的可用题数))`：五行 25 → 5、三爻 8 → 3、六爻本宫 8 → 3、六爻其余 56 → 6 | **一类知识有多少个可区分实例**（= 「要认多少个字」）。⚠️ 注意用的是**过滤后可用题数**，不是 `count`——量的是「这门课**覆盖的范围**」，而 `count` 只是每轮取样几道（同一课每次只做 5 道，但它覆盖的是 25 道的空间）。⚠️ **它不量单题难度**——所以只用于**排课顺序**，不用于积分权重（积分权重用 ②） |
| ④ | `difficulty` | 模板/题上已有的 `入门` / `进阶` | 既有的人工标注，**降级为次序键**（只在①②③全同时才起作用），避免与②重复计权 |

**为什么用「参数空间题数」而不是「选项数」：** 三种题的选项数分别是 5 / 8 / 6（都 ≈ 3 bit），**区分不了任何东西**；而参数空间是 25 / 8 / 64，正是「这门课要覆盖多少内容」的度量。这个选择有代价（见 §5.5），但它至少**是一个真的从内容库算出来的量**。

### §5.3 首批内容的实际曲线（用真实数据算给你看）

**拿现在库里的 3 个题组算**（六爻那个按 §3.3 的 `table-filter` 拆成两课，所以下表和是 4 门课）：

| 课 | 题源 | 可用题数（过滤后） | ① stage（建议值） | ② 认知负荷 | ③ 空间量级 | ④ difficulty | `sort_key` |
|---|---|---|---|---|---|---|---|
| 五行生克关系与方向 | `tpl.b0.s4.wuxing-relation` | 25 | 0 | 3（关系判断） | 5 | 0（入门） | `[0, 3, 5, 0]` |
| 由三爻定八卦 | `tpl.liuyao.trigram` | 8 | 1 | 3（关系判断） | 3 | 0（入门） | `[1, 3, 3, 0]` |
| 六爻定本卦·本宫位次 | `tpl.liuyao.hexagram` + `filter: 本宫` | 8 | 2 | 3 | 3 | 1（进阶） | `[2, 3, 3, 1]` |
| 六爻定本卦·其余位次 | `tpl.liuyao.hexagram` + `filter: 其余` | 56 | 2 | 3 | 6 | 1 | `[2, 3, 6, 1]` |

**词典序结果：** 五行 → 三爻 → 六爻(本宫) → 六爻(其余)。与直觉一致，且**每一步都能指出它为什么排在后面**。

> **`stage` 的建议值（0/1/2/2）是教学判断，需要你确认**（§11 清单第 3 项）。注意我**没有**把六爻那 64 题当一门课：拆成「本宫 8 题」与「其余 56 题」是本文档对 A7 的直接回应——**64 题平铺本身就是缺口，拆课靠的是 `rule.table` 里已有的 `position_kind` 列**（§3.3）。

### §5.4 CI 可校验：单调性（R27）

排序键是纯函数（输入只有 `bundle`），所以**「课程顺序与难度倒挂」是可以构建失败的**：

| 检查 | 规则 | 例子：什么会被拦下 |
|---|---|---|
| 同一 `Path` 内，`Unit` 序列的 `sort_key` 不得递减 | R27 | 把「六爻定世应」排在「三爻定八卦」前面 |
| 同一 `Unit` 内，`Lesson` 序列的 `sort_key` 不得递减 | R27 | 把 64 题的那一课排在 8 题那一课前面 |

**为什么定为 error 而不是 warning：** 排序键里没有主观量（②③④ 全是算出来的，① 是作者显式声明并在同一 Path 内比较），倒挂只可能是**写错了或没想清楚**。把它降成 warning 就等于允许「课程顺序随机」。

**歧义的边界（诚实标注）：** 若两课的 `sort_key` **完全相等**，R27 不做任何判断（允许并列）——课程设计者可以在同一档位内自由排序。**这是宽松的，不是遗漏。**

### §5.5 这套数也是「拍的」——但校准输入已经就位

| 拍的成分 | 校准输入（已存在） |
|---|---|
| ② 认知负荷权重 1/2/3/4/5 | **耗时**（`Attempt.latency_ms` → `analysis.latencyByKind`）与**首次答对率**（`exerciseStats`）。`docs/待采集数据.md` 表 2 已把这两项列为「✅ 数据能校准」 |
| ④ `入门/进阶` 的 1.0 / 1.5 权重 | 同上（首次答对率） |
| ③ 用 `log2(题数)` 近似「内容量级」 | **它是我拍的代理量**，风险明确：**答案空间大但直觉可判**的题会被算难（例：五行题 25 道，但方向靠两条闭循环就能推）。真正该用的是**首次答对率**——而那需要两周数据 |

> **所以本文档的姿态是：先用可计算量建一条**可用的**曲线，把它标成待校准，而不是等数据。** 这与 `docs/待采集数据.md` 的整体思路一致（「攒的是我自己拍的那些数值的实测校正」）。**若数据表明 ③ 完全指错方向，改的是一行排序键，不是课程内容。**

## §6 「流派对比」课程形态

### §6.1 它是什么（照抄既定口径，不重新定义）

V0.1 §16.2 的原话：

> 它不是「更难的同一门课」，而是**结构性不同的课**：并列多个流派的处理方式，教学目标是「理解分歧点在哪、分歧为何存在」，**不是「记住哪个对」**。

ADR-0006 补充了它在阶段上的位置：入门锁定一个 `default_school`（界面干净），**达到 B2 后解锁对比**。

### §6.2 与普通 Unit 的差别（七条，逐条可落地）

| # | 差别 | 落成什么数据 |
|---|---|---|
| 1 | 目标不是「会做某个操作」，而是「能指出分歧」 | `unit_kind = '流派对比'` + `Lesson.divergence_rule_ids` |
| 2 | 并列 ≥2 派 | `Lesson.school_ids`（≥2；例外见 §6.4） |
| 3 | 必须有能力前置（不得从零进入） | 该单元**入口课**（`entry_lesson_id`）的 `unlock_rule` 不得为 `entry`，且必须含 `mastery_threshold` 或 `path_mastery`（R24） |
| 4 | 判分规约不同：`school_variance` 从「容许差异」升级为「**考查差异**」 | 复用已有字段：`AssessmentSpec.is_school_comparison` + `Rubric.is_school_comparison`（两个字段都已存在，**不需要新增**） |
| 5 | `must_hit` 里必须出现「指出分歧点」 | **建议给 `Rubric` 新增一个字段** `must_hit_divergence: string[]` —— 见 §6.6 |
| 6 | 新题型：「指出分歧源于哪一步规则」 | `divergence_rule_ids`（指向 `Rule`。`Rule.school_id` 已是一等字段，V0.2 §5.5 就是为这个场景定的） |
| 7 | 同一卦例在两派下结论不同 | 课的题源必须包含**同一输入的两次不同判分**：用 `reference_case` 表达（见下） |

**`reference_case`（流派对比课的题源扩展）：**

```json
{
  "reference_case": {
    "rule_ids": ["rule.liuyao.hexagram-by-yao", "rule.xxx.school-b-取用神"],
    "input": { "lines": [1,1,1,1,1,1] },
    "note": "同一卦例，两派取法不同 → 结论不同。分歧点在 rule.xxx 这一步"
  }
}
```

> **为什么用 `rule_ids` 对而不是复制两个答案：** 答案由规则引擎算（V0.1 §12：有唯一答案处不用 AI）。若课程把「甲派答 A、乙派答 B」写死，就等于把规则引擎的输出抄了一份（违反 L2），而且改规则表时课程不会跟着变。**同一 `input`、两条 `Rule`、两个输出**——这才是「分歧源于哪一步规则」的正确表示。

### §6.3 需要额外实体吗？—— 不需要

**倾向：不新增实体。** 流派对比所需的一切都能挂在**已有实体**上：

| 需要表达的东西 | 挂在谁 | 是否新增字段 |
|---|---|---|
| 这是对比课 | `Unit.unit_kind`、`AssessmentSpec.is_school_comparison`、`Rubric.is_school_comparison` | 仅 `unit_kind` 是新字段（Unit 本来就要新设） |
| 对比哪些流派 | `Lesson.school_ids` | 新字段（Lesson 本来就要新设） |
| 分歧落在哪一步 | `Lesson.divergence_rule_ids` | 新字段 |
| 两派的取法差异 | `School.stance` + `School.anchor_sources[]`（**已有**） | ❌ |
| 流派变体与冲突 | `relations` 里的 `variant_of` / `contradicts`（**已有**） | ❌ |
| 判分标准的差异 | `Rubric.school_variance`（**已有**） | ❌ |

> **新增一个 `SchoolComparison` 实体的代价**：它要重复 Unit/Lesson 的层级与顺序表达，且与 `Unit.unit_kind` 二选一——两处真相。**不做。**

### §6.4 两种分歧，必须分开：跨流派 vs 体系内部不自洽

ADR-0015③ 定了一件事：**梅花易数的体用取法「本身不自洽」，这件事要作为 B2 第一课的内容，而不是隐藏**（依据 R1 Q4.2：林俊岑文指出该书占法「取法本身不自洽」，置信度中，有争议）。

这与「甲派 vs 乙派」是**两种不同的课**：

| `divergence_kind` | 含义 | `school_ids` | 教学表述 |
|---|---|---|---|
| `inter_school` | 两个可引证文献的流派对同一操作取法不同 | **≥2**（且都属于同一 `system_id`） | 「依据《增删卜易》一路的取法是 A；依据《卜筮正宗》一路的取法是 B」（ADR-0012：流派必须以可引证文献为锚） |
| `intra_school_inconsistency` | **同一部文献内部**的取法自相矛盾 | 允许 = 1 | 「这部书自己的取法不一致——这本身是教学内容」（ADR-0015③） |

**为什么必须有这个分支：** 若强行要求 `school_ids ≥ 2`，「梅花体用不自洽」这一课就**建不出来**——而它恰好是 ADR-0015③ 指定的 B2 第一课。

### §6.5 内容卡在哪：这门口号课**现在开不了**

**必须说清楚，否则 V0.4 会看起来像「做完就能上流派对比课」。**

| 对比课需要什么 | 现在有吗 | 卡在哪 |
|---|---|---|
| 同一体系下 **≥2 个以文献为锚的流派** | ❌ **库里那 2 个 `School` 分属两个不同体系**：`school.liuyao.zengshanbu`（《增删卜易》一路）属六爻、`school.meihua.tongxingben`（《梅花易数》通行本一路）属梅花，各自是自己体系的 `default_school`。**同一体系内部一派都没有第二个** | 需要第二条**可引证文献**的取法，且要能给出它的 `anchor_sources`（ADR-0012）。这正是 ADR-0006「入门锁定单一流派」的直接后果——对比课的成本就是补齐第二派的文献 |
| 两条 `Rule` 对**同一输入**给出不同结果 | ❌ | 需要**六爻取用神/纳甲/旺衰**这类规则，而它们全部卡在文献上：缺口清单 **A1 六亲**（缺纳甲地支）、**A2 纳甲**（需《增删卜易》/《卜筮正宗》**正文**）、**A3 旺衰**、**A4 冲合**。R1 只核实了书名与作者 |
| 梅花体用不自洽那一课 | 🔶 方向已定（ADR-0015③） | 需要《梅花易数》体用相关段落的**具体文本**与来源定位；R1 给的是二手结论（林俊岑文），按认识论原则 3 需升级来源 |

> **所以 V0.4 的交付边界是：把「流派对比」变成**结构上可表达、CI 上可校验、内容上等待文献**的形态。** 第一门对比课的内容不在本文档范围内，也不该由本文档生成（认识论原则 3 / 工作方式约定 5）。

### §6.6 一个字段建议：`Rubric.must_hit_divergence`

**问题：** R24 要校验「对比课的 Rubric 必须考查分歧」，但 `must_hit` 是自由文本数组（现实例：`"指出这条对应是 19 世纪西方秘教传统的**建构/归赋**..."`）。

| 方案 | 内容 | 评价 |
|---|---|---|
| A（**推荐**） | 给 `Rubric` 新增 `must_hit_divergence: z.array(z.string()).default([])`；`is_school_comparison = true` 时 CI 要求它**非空** | 结构清晰；校验精确；与 `school_variance` 的升级语义（「容许」→「考查」）对应 |
| B | 对 `must_hit` 做子串匹配（要求含「分歧」二字） | 零 schema 改动，但**脆弱**：文案里出现/不出现「分歧」二字完全靠作者措辞，改一个字就红/绿。这类「文案敏感」的校验在项目里已有教训（R3 曾是死规则） |
| C | 不校验，只写在文档里 | 等于没有这条约束 |

> **倾向 A。** 代价：**对已定 schema 的一处加法**（`Rubric` 是新字段，不是三大定案之一，成本低）；需要同步 `rubric.astro-reconstruction`（它是 `is_school_comparison = false`，**不受影响，不用改**）。

## §7 需要新增的 CI 规则（R21–R28）

**编号延续 R1–R20。** 现有 22 条是 `R1a/R1b/R1c + R2–R20`，插入方式与 `rules.ts` 完全一致：`RULE_BASIS` 加一条，`validateBundle` 里加一段，**并且每条规则至少有一条能触发它的测试**（step 1 的验收标准原文：「9 条 CI 规则全部有对应测试且都能被触发——否则规则只是注释」）。

|---|---|---|---|
| **R21** | **课程结构引用完整性**：`Path.unit_ids` / `Unit.lesson_ids` / `Lesson.question_sources[].template_id` / `Lesson.exercise_ids` / `Lesson.skill_ids` / `Lesson.assessment_spec_id` / `Lesson.school_ids` / `Lesson.divergence_rule_ids` / `unit.system_id` / `path.system_id` 任何一条悬空 → 失败。**实现上直接复用 R10 的 `ref()` 辅助函数**（同一套语义、同一套报错格式） | V0.1 §14 流水线 ② 引用完整性 | error |

| **R26** | **B0 样本准入（ADR-0013 的落地）**：① `unit_kind = '基础'` 的课**必须**声明 `sample_kind`；非基础单元的课**不得**声明 ② `sample_kind = 'B'` 时，该课引用的内容（题源模板 / 手写题 / 其 Skill 的 `system_id`）**必须**能追到 `school_id` 或 `controversy_flag = true`——缺则失败。③ `unit_kind = '基础'` 时 `system_id` 必须为空 | ADR-0013（M18）；V0.2 §2.2 | error |
| **R27** | **难度单调性**（§5.4）：同一 `Path` 内 `Unit` 序列的 `sort_key` 非递减；同一 `Unit` 内 `Lesson` 序列的 `sort_key` 非递减。并列（相等）允许。报错时**必须打印两个 sort_key 的分项**，否则人看不懂 | V0.1 §6（阶段）、§10.1；本文档 §5 | error |
| **R28** | **课程文案必须进 `content_texts`**：`Lesson.title` / `Lesson.summary` / `Unit.goal` / `Path.goal` 每个非空自然语言字段，必须存在一条 `content_texts` 条目且 `owner_id = <该实体 id>` → 否则失败。**依据：R9（禁用语检查）只扫 `content_texts`**——课程文案若留在实体字段里就绕过了「一定/必然/百分百」这类确定性话术筛查（V0 伦理边界 4），那是**检查盲区** | V0.1 §14 禁用语检查；V0 伦理边界 | error |

**新增后规则数：22 + 8 = 30**（实现后跑 `pnpm facts` 核对；若显示 29，先检查是否有规则漏了引号）。

**伦理必修的 CI（有意暂不做）：** V0 §四.2 要求「面向他人的伦理准则必须是课程内容，且是**必修关卡**」。严格执行它需要「沿 `unlock_rule` 图 + Unit/Lesson 归属关系做传递可达性搜索：凡 `stage = 6`（独立实战）的 Unit，必须传递依赖一个 `unit_kind = '伦理必修'` 的 Unit」。
> **倾向：现在不写这条规则。** 理由：库里**没有任何 `stage = 6` 的 Unit**，规则写出来就是一条永远不会触发的死规则（R3 的教训）。**写进本文档，并在第一个实战单元落地时同步实现。** 代价：这段时间内伦理前置只靠人工保证。**这是明确的欠账，不是遗漏。**

### §8.4 有没有破坏性变更？—— 结论：没有

| 改动 | 是否破坏 | 说明 |
|---|---|---|
| 新增三个顶层键 | ❌ | **纯加法**。zod 的对象 schema 里新键是必填数组——所以**旧 bundle 会校验失败**（缺键）。这就是 `version` 要不要 bump 的问题（见下） |
| `Attempt` 加两个 `optional` 字段 | ❌ | 可选字段是加法；IndexedDB 的 `DB_VERSION` 提升即可。**现在真实作答数据为零**（缺口清单 E6），这是唯一一个「改动成本最低的窗口期」 |
| `Rubric` 加 `must_hit_divergence`（默认 `[]`） | ❌ | 有 `.default([])`，既有 `rubric.astro-reconstruction` 不用改 |
| 首批课程内容 | ❌ | 全部是 `draft`（与现有内容一致，无法也不需要升 `reviewed`） |
| R1c 豁免范围扩大 | ⚠️ 语义变化，非破坏 | 课程实体不再因「无来源」收到 warning。**这是有意的**（§1），且不影响任何既有条目 |

**`bundle.version` 要不要从 2 提到 3？**

| 方案 | 理由 | 代价 |
|---|---|---|
| **A（推荐）bump 到 3** | 顶层形状变了（多了三个必填数组键），版本号是可用来区分「有没有课程结构」的唯一标记。`contentBundleSchema` 里 `version` 是 `z.number().int().positive()`——**现在没有任何代码用它做分支**（已核对：全仓只有 `store.ts` 的 `db_version` 是另一回事），所以 bump 只花一行 | 无实际代价 |
| B 保持 2 | 更省事 | 事后无法从版本号判断一份导出/落库数据是否含课程结构 |
| C 让三个键 `.default([])` 以兼容旧 bundle | 旧文件能加载 | **反对**：默认值会让「忘了写课程结构」静默通过——而 `emptyBundle()` 的测试会变绿，CI 会以为一切正常。**宁可校验失败** |

> **倾向 A。** **代价：** 若将来有外部脚本断言 `version === 2`，需同步（现在没有）。**这条要你确认**（§11 清单第 1 项）。

### §8.5 首批落地的课程内容（建议值）

```
path.liuyao.rules-first（六爻 · 规则密集型入门）
├── unit.b0.s4                    基础 · stage 0 · 无 system_id
│   └── lesson.b0.s4.01           5 题（strided / 25 题空间）· sample_kind A
├── unit.liuyao.trigram           普通 · stage 1 · system.liuyao
│   └── lesson.liuyao.trigram.01  8 题（all）
└── unit.liuyao.hexagram          普通 · stage 2 · system.liuyao
    ├── lesson.liuyao.hexagram.01 8 题（table-filter: 本宫）
    └── lesson.liuyao.hexagram.02 10 题（strided / 其余 56 题）
```

- **总题数不变**：97 题仍然可玩，只是从「下拉框里的 3 个并列项」变成「1 条路 + 3 个单元 + 4 课」。其中六爻那 64 题按 `position_kind` **互斥地切成两课**（本宫 8 题 / 其余 56 题里取 10 道）——**这是切分而不是重叠**；重叠只会在「将来第二门课沿用同一题源」时出现，而那是允许的（§3.4）。
- **每课一个 `assessment_spec_id`**：复用现有的 `spec.b0.s4` / `spec.liuyao.trigram` / `spec.liuyao.hexagram`，**不新增规约**。
- **每课的 `completion_rule`**：`mastery_threshold`（dimension = `应用`，因为 `evidenceFromAttempt` 对 `关系判断` 题型给出的维度就是 `应用`——见 `mastery.ts` 的映射），`min_value` 建议 `0.8`，`min_samples = 3`。**`0.8` 是拍的**，与难度权重一样进待校准清单。
- **`unit.b0.s4` 的 `sample_kind`**：五行生克是**方向性操作**，属 ADR-0013 的 **A 类（流派无关的符号层操作）**——这一点在 ADR-0013 里有明确列举（「五行生克的**方向**」）。所以它**不需要** `school_id`，R26 会通过。

## §9 分步实施计划（每步可独立验证）

> 原则：**每一步做完都能用一条命令判定成败**，且失败时有明确的现象可看。

| step | 产出 | 怎么验证（做完就跑） | 失败长什么样 |
|---|---|---|---|
| **0** | 本文档评审通过 + **ADR-0025** 记入 README §四（另一位作者更新 README） | 人工评审；把 §11 的三项拍定 | 评审未过则往后全部作废（与 V0.2.1「不定无法开始写 schema」同理） |
| **1** | 三个 zod schema + `bundle.ts` 顶层键 + `emptyBundle()` + `index.ts` 导出 | `pnpm typecheck` 干净；`pnpm -r test` 全绿；加一条测试：**故意删掉 `lessons[0].unlock_rule` → `safeParse` 必须失败** | `emptyBundle` 漏键 → `packages/domain/test/bundle.test.ts` 直接红 |
| **2** | 首批 1 Path / 3 Unit / 4 Lesson 写进 `bundle.json`（全 `draft`） | `pnpm --filter @dlg/content validate` 通过且**内容计数出现 `paths/units/lessons`**；`pnpm --filter @dlg/content count` **仍是 97 题**（编排不改内容量——这是关键回归断言） | 题数变了 = 编排动到了内容，立刻回退 |
| **3** | CI 规则 **R21–R28** + `layer0Groups` 三类 + R1c 豁免 | ① `pnpm facts` 的规则数显示 **30** ② `pnpm -r test` 全绿 ③ **每条规则至少一个能触发它的用例**（照 step 1 的标准） | 规则数显示 29 → 有规则漏了引号（§7 的坑） |

| **5** | `course/unlock.ts`：`evaluateUnlock` **三态** | ① 零 evidence → 全部 `判定中`，且给出「再做 3 题才能判定」② 3 条全对 evidence → `已解锁`，`应用` = 1.0 ③ 2 条 evidence（样本 2）→ 仍 `判定中`，**不得返回数字** ④ 断言：**任何返回值里都不出现积分**（接口层面保证 §4.4） | 样本 2 时返回了 0.5 → 违反「不给假数字」 |
| **6** | 预览站课程导航（Path → Unit → Lesson + 解锁状态）+ `drill.ts` 改用 `selectInstances` | ① `pnpm --filter @dlg/preview contrast` 通过（新的 UI 元素也要过对比度门）② 构建冒烟测试通过 ③ **手工点一遍**：首课可进、后续课显示「判定中 / 需要再做 N 题」④ 落库导出 JSON 里出现 `lesson_id` | 冒烟红 = 产物里引用了 DOM 替身没有的 API（`store.ts` 的降级路径要照顾到） |
| **7** | 流派对比课的**结构**落地（建一个 `unit_kind = '流派对比'` 的空壳单元 + 一份 `is_school_comparison = true` 的 `AssessmentSpec`/`Rubric`） | ① `pnpm validate` 通过 ② **故意把 `is_school_comparison` 改成 `false` → R24 必须报错** ③ 内容层面**明确标注**：这门课**没有题**（`question_sources` 为空会触发 R22，所以此步只做结构单元的测试夹具，**不进 `bundle.json`**） | R24 不报错 = 规则没接上 |

**step 7 的说明：** 流派对比的**内容**进不了（§6.5 文献卡点）。所以 step 7 交付的是「CI 能拦住一个假的对比课」，而不是一门真课。**这是刻意的边界**——写一门假课的样板进内容库，比没有更糟（它会让 `pnpm facts` 的内容量看起来变多，而实际不可玩）。

## §11 需要你拍定的三件事

按项目习惯，每条给**倾向 + 理由 + 代价**。三项都定了就能开工 step 1。

### 1. `bundle.version` 2 → 3？

- **倾向：** 提到 **3**。
- **理由：** 顶层形状变了（多三个必填数组键），版本号是唯一能区分「这份 bundle 有没有课程结构」的标记；而全仓**没有任何代码**用 `version` 做分支，bump 的成本是一行。
- **代价：** 若将来有外部脚本断言 `version === 2`，需同步（现在没有）。
- **反方案（我不建议）：** 让三个键 `.default([])` 以兼容旧文件——那会让「忘了写课程结构」静默通过。

### 2. 混淆对是否进通关判据（与 V0.1 §10.1 的偏离）

- **倾向：不进判据，只做「推荐下一课」的非阻塞提示。**
- **理由：** §4.5 三条（它把内容缺陷变成用户门槛；它是与六维向量不同源的聚合量；它现在恒为 0）。
- **代价：** 失去「拦住带着系统性混淆继续走」的保险；且 V0.1 §10.1 需按本文档修订（**这一处修订需要你同意**，因为它改的是已写进 V0.1 的判据示例）。
- **若你选「进判据」：** 我需要额外定义「混淆对频率」的分母与窗口（按题？按会话？按近 N 天？），那是一套新尺度——**我会要求先写一条 ADR 把尺度定下来再动手**。

### 3. 首批课程的 `stage` 与 `min_value` 建议值

- **倾向：** `unit.b0.s4 = 0`（B0 基础层）、`unit.liuyao.trigram = 1`（符号识字）、`unit.liuyao.hexagram = 2`（属性与关系）；`completion_rule.min_value = 0.8`、`min_samples = 3`。
- **理由：** stage 对应 V0.1 §6 的阶段定义（0 = 象数素养体系无关、1 = 符号识字、2 = 属性与关系）；`min_value = 0.8` 与 V0.1 §10.1 示例里的「识别 ≥ 80」同一量级。
- **代价：** **它们全是拍的**，与认知负荷权重、掌握度门槛一样进待校准清单（`docs/待采集数据.md` §二）。校准输入已就位（首次答对率 + 掌握度时间序列）。
