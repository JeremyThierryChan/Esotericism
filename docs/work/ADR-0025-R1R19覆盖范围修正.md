# ADR-0025 · R1/R19 的覆盖范围修正（两个实体此前完全没被检查）

> 状态：**✅ 已实现**
> 依据：ADR-0022（复核记录 `verifications` 一等化 + CI 规则 R19）
> 代码：`packages/domain/src/validate/rules.ts`（`layer0Groups`）· `packages/domain/test/validate.test.ts`
> 发现方式：写内容流水线工具（ADR-0026）时，工具需要「哪些条目可以签字」，于是把 62 条带 provenance 的条目逐条推进校验器 —— 结果发现有两组**从来没人检查过**

---

## 一、问题

`validateBundle` 里 R1a/R1b/R1c/R19 是靠一张 `layer0Groups` 表决定「检查哪些实体」的：

```ts
const layer0Groups = [
  ['formalism', …], ['attribute_space', …], ['symbol', …], ['system', …],
  ['school', …], ['concept', …], ['schema', …], ['rule', …], ['skill', …],
  ['rubric', …], ['assessment_spec', …], ['relation', …],
];
```

**`exercise` 与 `exercise_template` 不在里面**，而两者的 schema **都**继承自 `entityBaseSchema`
（也就是都带 `provenance`），内容库里也各有 3 条。

后果不是「少一个警告」，而是：

> **一道题可以被直接标成 `review_status: 'reviewed'` 而不需要任何人工复核记录，CI 照样通过。**

而题目正是玩家实际作答、最该有人签字的对象 —— ADR-0022 引入 R19 的全部意义恰好在这里泄漏。

---

## 二、修复

往 `layer0Groups` 补两行：

```ts
['exercise', bundle.exercises],
['exercise_template', bundle.exercise_templates],
```

并补 5 条回归测试（`validate.test.ts` 的「R1/R19 覆盖范围」一组）：

| 用例 | 断言 |
|---|---|
| exercise 处于 reviewed、无复核记录 | 报 **R19** |
| exercise 处于 reviewed、只有 AI 复核 | 报 **R19** |
| exercise 有「人工 + 证实」 | **不**报 R19（正向对照，防止测试只会红） |
| exercise_template 处于 reviewed、无复核 | 报 **R19** |
| exercise 处于 reviewed、来源为空 | 报 **R1a** |
| exercise 处于 reviewed、`authored_by = ai-candidate` | 报 **R1b** |
| exercise 处于 draft、无来源 | 只警告 **R1c**，不阻塞（草稿阶段必须能存在） |

**测试是先验证过会红的**：把两行改动临时撤掉，5 条里有 4 条立刻失败（第 3 条正向对照仍然通过）。
这一步是必要的 —— 否则写出来的可能是一条永远绿的测试。

补上这两行**没有引入任何新警告**：6 条 exercise / exercise_template 都各自带着 1–2 条来源。

## 三、顺带记录：`transfer_edges` 结构上无法签字（未修，列为 T8）

同一轮排查发现另一处不一致，但**性质不同**，所以这一轮不动它：

`TransferEdge` 自带 `sources` + `source_strength`，却**没有 `provenance`**。于是它：

- 没有 `review_status` → 无法被标记 `reviewed`
- 没有 `verifications` → **无法留下人工签字**
- 因此 R19 对它无从生效，只有单独的一条 R1a（`sources` 非空）约束它

也就是说：**我们唯一那条跨体系迁移边（塔罗「力量」↔ 狮子座）永远停在「有来源但无人复核」的状态**，
而它恰恰是认识论风险最高的一类内容（`historicity = 重建`，见 R1）。

**为什么这一轮不修**：把它改成带 `provenance` 是 **schema 变更**，会触及
`transferEdgeSchema`、`bundle.json` 里那条边、以及若干读取 `e.sources` 的代码路径。
按项目惯例（`docs/冷启动.md` §五 第 6 条：改 schema 前先改 ADR），这类改动要单独立项。
已登记为缺口 **T8**。

## 四、连带发现：`SymbolUsage` / `has_attribute` 也不带 provenance（待拍定）

这两组「连接表」在 schema 里同样没有 `provenance`。本轮在 `rules.ts` 的注释里把它们记为
「边/连接表，无独立来源主张」—— **但这是个待拍定的判断，不是已定案的事实**：

V0.5 文档（`docs/V0.5-练习系统.md` §8.2 R26）指出，**迁移预测题的题池直接由 `SymbolUsage` 决定**：

> 「某体系以什么角色使用某符号」本身就是一个**知识论断**（例如「六爻以火为卦宫五行」）。
> 如果扩题池 = 往 `symbol_usages` 里加条目，那「无独立来源主张」这个说法就站不住了 ——
> 等于批量制造没有来源记录的考点。

两种判断不能都成立。**本轮不改代码，只把注释里的断言降级为待拍定**，
以免后来的人把它当成已定案的设计依据。
