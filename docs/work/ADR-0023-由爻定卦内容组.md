## 二、表驱动规则：让查表类规则的数据回到内容库

V0.2 §6 早就识别出「查表类规则」是与纯算法不同的一种规则形状（spike 时特意选 L6.1 定世应来验证这一点）。
本轮把它落地：**`Rule.table`** —— 带列定义的数据表。

```ts
ruleTableSchema = {
  description: string,
  columns: [{ key, label, type: 'string'|'number' }],
  rows: Array<Record<string, string|number>>,
}
```

**为什么必须有列定义**：`z.unknown()` 存表等于放弃校验。**64 行的卦序表，手抄错一行是看不出来的** ——
而这正好是最难发现的坏数据（有题干、有选项、判分还能通过）。CI 规则 **R20** 逐行校验列齐全与类型。

**表也不是手抄的**：两张表由脚本从 `packages/domain/src/liuyao/tables.ts`（已核对过的数据）程序化导出。

### 生成器扩展：`bit-combinations` 模式

原有生成器只会出「两个符号之间的关系题」。新增 `parameter_space.mode`：

| 模式 | 用途 | 枚举方式 |
|---|---|---|
| `symbol-pairs` | 五行生克 | 符号的有序对（含自身） |
| **`bit-combinations`** | 三爻→八卦、六爻→本卦 | 位组合全部 2ⁿ 种 |

并新增 `answer_field`（答案取规则输出的哪个字段）与
`choices_mode: 'answer-field-distinct'`（选项 = 规则表里该字段的**去重取值**）。

> **选项必须与规则的可能输出同源**，否则会出「正确答案不在选项里」这种坏题 ——
> 有测试逐题断言「正确答案一定在选项里」。

### `RuleProcedure` 签名扩展

规则过程现在拿到**自身声明**：`(input, ctx, rule) => unknown`。
理由很实际：表驱动规则需要读**自己那张表**（`rule.table`），而 `ctx.bundle` 里有多条规则，procedure 无从知道自己是哪一条。

## 五、一个建模决定，以及它留下的问题

**决定：卦名（64 个）目前只存在于规则表里，未建模为 `Symbol`。**

理由：
- 当前技能是**推导型**（「由爻定卦」，V0.2 的 L2.1/L6.1），答案是**算出来的**，不是指认出来的
- 若把 64 卦建成 Symbol，就需要表达「上卦 + 下卦」的**构成关系** ——
  而 Layer 1 目前**没有复合结构实体**（`Relation` 的 `related_by` 只涵盖 生/克/冲/合/相位/互卦/牌序，
  都是**独立对象之间的互动**，不是「由…构成」）

**留下的问题（做「指认卦名」类技能时必须解决）**：

| 方案 | 说明 |
|---|---|
| A. 新增 `composed_of` 关系类型 | 复用既有「通用边」设计（`Relation` 已是多类型边），最轻 |
| B. 新增 Layer 1 实体 `Structure`（复合结构） | 更正统：卦/牌阵/星盘都是「多个符号按位置组成的结构」，S5 组合成局需要它；但改动大 |

**我倾向 A**（`composed_of` + `role: upper/lower`），理由是改动最小且与既有设计一致；
但若日后要做牌阵/星盘（V0.1 §5.3 都提到），B 可能更省事。**这个决定可以推迟到真的需要指认卦名时再做** ——
现在不做，是因为没有技能需要它（`YAGNI`）。
