## C. 技术实现缺口

### C1. Layer 3/4 里声明了但没实现的实体

V0.1 §2 定义的四层里，这些**还没有落库对象**：

| 层 | 已实现 | **未实现** |
|---|---|---|
| Layer 3 教学层 | Exercise · AssessmentSpec · Rubric · ExerciseTemplate | **`Path` · `Unit` · `Lesson`** |
| Layer 4 用户状态层 | Attempt · Evidence · JudgeAudit · Mastery(计算) · 积分 | **`User` · `UserConceptState` · `UserSkillMastery`(实体) · `ConfusionPair` · `ReviewItem`** |

> 这两个缺口是同一种病：**「声明了但没有落库对象」**。前两次已经踩过——step 2 缺 `Exercise`、
> step 3 缺 `Attempt`，都是到「要用了」才发现。`Path/Unit/Lesson` 会在做 V0.4 时立刻需要；
> `ReviewItem/ConfusionPair` 会在做 V0.6 时立刻需要。
>
> ⚠️ **第三次踩到了同一个病，而且更隐蔽**（ADR-0025）：`Exercise` 与 `ExerciseTemplate`
> 的 schema **都带 `provenance`**，数据里也各有 3 条 —— 但它们**不在 `validateBundle` 的
> `layer0Groups` 名单里**，于是 R1a/R1b/R1c/R19 对它们**完全不生效**。
> 后果不是「少一个警告」：**题目可以被标成 `reviewed` 而无需任何人工复核记录，CI 照样通过**。
> 也就是说「声明了但没有接上」不只发生在**实体**上，也发生在**校验名单**上。
> 这一类漏检不会自己报错，只会静默放过 —— 所以现在有 7 条回归测试锁住它。

```bash
pnpm facts        # 权威数字 + 审核状态 + 可生成题数 + **签字就绪度**（含阻塞按规则聚合）
```

`pnpm facts` 现在会打印「签字就绪度」一节（来自内容流水线工具的 `check`），
它直接回答「现在能签几条、卡在哪条规则」—— 这是本清单里**最容易过期的那几栏**的替代品。

**其余核对命令：**

```bash
# 内容实体计数
python3 -c "import json;b=json.load(open('packages/content/bundle.json'));[print(k,len(v)) for k,v in b.items() if isinstance(v,list)]"

# CI 规则清单（22 条）
# ⚠️ 必须用 'R..' 带引号匹配：R10 是作为函数参数传入的（ref('R10', ...)），
#    用 "R[0-9]+[a-c]?:" 会漏掉它，得出 21 这个错误数字。
grep -oE "'R[0-9]+[a-c]?'" packages/domain/src/validate/rules.ts | sort -u | tr '\n' ' '

# 测试与类型（4 个包/应用）
pnpm -r typecheck && pnpm -r test

# 内容审核状态（应为 0 个 reviewed，直到人工签字）
pnpm --filter @dlg/content validate

# 只想知道「能不能签字」，不开界面
pnpm --filter @dlg/studio check

# 内容流水线工具的端到端冒烟（真起服务真发请求）
pnpm --filter @dlg/studio build
```

> **本清单的维护规则**：能被 `pnpm facts` 打印出来的数字，**不要写进本文件**；
> 确需快照就注明日期。上面「一页速览」里保留的数字是为了让人一眼看到量级，
> 一旦与 `pnpm facts` 不一致，**改本文件，不要改脚本**。
